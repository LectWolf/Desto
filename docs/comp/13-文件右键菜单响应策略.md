# 文件右键菜单响应策略

## 问题

Windows Shell 的 `SHParseDisplayName`、`SHBindToParent`、`GetUIObjectOf(IContextMenu)` 和 `QueryContextMenu` 都可能同步加载文件类型及第三方 Shell 扩展。旧实现为了判断核心 verb 是否存在，在显示 Win11 紧凑菜单之前就完整执行这条链；任何缓慢扩展都会直接表现为“右键后菜单迟迟不出现”。把同一 COM 对象简单移到后台线程不可行，因为 Shell handler 具有 COM apartment、所有者窗口和菜单消息转发约束，异步结果还可能在用户已经取消菜单后到达。

## 当前策略

Windows 11 且未启用经典菜单覆盖时，首次右键只命中文件项、复制必要的 Card/Item 标识和路径，并用 `ShowWindowsPopupMenu` 同步显示固定核心入口：打开、剪切、复制、删除、属性、显示更多选项。该阶段不解析 PIDL，不访问 `IShellFolder`，不创建 `IContextMenu`，因此第三方 Shell 扩展不在首帧响应路径中。

选择打开、剪切、复制、删除或属性后，才建立文件自己的 `IContextMenu`，以 canonical verb 查找实际命令并调用 `InvokeCommand`。Desto 不提供文件项原位重命名；选择“显示更多选项”后才执行 `QueryContextMenu` 并转发 `IContextMenu2/3` 菜单消息，完整菜单及扩展项仍由 Windows 负责。

Windows 10、旧系统或用户主动启用经典菜单覆盖时，保留直接查询并展示完整 Shell 菜单的行为。这里优先尊重系统菜单偏好，不能用快速紧凑菜单替换用户明确选择的经典菜单。

## 拖放操作

文件拖放会把 OLE `keyState` 从 `DragEnter`、`DragOver` 和 `Drop` 原样传到宿主。普通拖动在目标允许时返回 MOVE；按住 Ctrl 且目标允许 COPY 时返回 COPY，并由同一操作值选择真实文件事务。复制使用递归 `FileCopyTransaction`，源项目和源卡片缓存保持不变；移动继续使用 `FileMoveTransaction` 并通知 Shell 缓存迁移。卡片内排序拖动不因 Ctrl 变成复制。

## 成本与释放

- 首层紧凑菜单：固定数量的本地菜单项，无 COM/Shell handler 加载；菜单关闭后立即释放 `HMENU`。
- 核心命令：只在用户确认命令后产生一次 PIDL、Shell Folder 和 Context Menu 按需成本；命令调用结束立即释放。
- 显示更多/经典模式：成本与 Explorer 经典菜单同类，第三方扩展延迟仍由对应 handler 决定，但不再阻塞 Win11 首层菜单。
- 常驻成本：无新线程、无线程池任务、无菜单缓存、无后台 COM apartment。

## 验收

- Win11 默认策略首次右键立即出现固定紧凑菜单。
- 取消首层菜单不会触发任何 Shell 查询。
- 核心命令仍以文件 handler 的 canonical verb 执行，不用 Desto 伪造文件操作。
- “显示更多选项”包含文件原有扩展项并能正常处理 owner-draw/submenu 消息。
- 经典菜单覆盖开启时，行为与修改前一致。
